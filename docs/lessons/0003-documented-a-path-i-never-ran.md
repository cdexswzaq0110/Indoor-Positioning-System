# 別在文件裡寫一條自己沒跑過的路

## 觸發情境

寫「之後要怎麼接完這個功能」的說明——那種本輪不做、但要交代下一步的段落。

## 領悟

我在 `mobile/README.md` 寫了完整的 TFLite 接法：裝 `react-native-fast-tflite`、
把 `ml/export.py` 產生的 `.tflite` 放進 `assets/`、走 EAS dev build。步驟具體、看起來可執行。

**然後真的跑 `ml/export.py` 的時候才發現，那個 `.tflite` 在這台機器上根本產不出來：**

```
ERROR LiteRT: export failure 0.0s: LiteRT export only supported on Linux x86 and macOS
```

【已確認：2026-09-03 實測，Windows + ultralytics 8.4.138】

我寫的不是一條「還沒走完」的路，是一條**在這個平台上不存在**的路。
如果沒有順手跑一次匯出，這段文件會一直留著，直到有人照著做、卡在第 3 步，
然後花時間懷疑是自己環境壞掉。

差別很微妙但很關鍵：
- 「這條路我還沒接完」——誠實的待辦。
- 「這條路長這樣，照著做就行」——**沒驗證過就等於在編**，即使每一步看起來都合理。

ONNX 匯出是通的（10.0 MB, imgsz 256），所以修正是把整條路改成 ONNX +
`onnxruntime-react-native`，並在文件裡留下「為什麼不是 TFLite」與那行實測錯誤訊息。

## 為什麼會撞到

因為那段文件寫在**匯出腳本寫完、但還沒執行**的空檔。腳本的程式碼是對的
（`model.export(format="tflite")` 語法完全正確），所以它讀起來沒有任何問題。
**壞的不是程式碼，是平台支援度——那是一個只有執行才會暴露的事實。**

順序上，我把「寫下一步的說明」排在「驗證下一步可行」之前了。

## 下一輪怎麼用

- 文件裡任何**具名的工具鏈**（套件名、檔案格式、指令），要嘛跑過，
  要嘛明講「未驗證」。不要讓沒跑過的步驟長得跟跑過的一樣。
- 交付物裡的「未來工作」段落，至少要驗證它的**第一個不可逆前提**——
  這次就是「這個格式匯得出來嗎」。後面的步驟可以留待辦，但前提不能用猜的。
- 這條跟 [[0001-preflight-changed-two-decisions]] 是同一個病的兩種發作：
  環境事實與計畫衝突。0001 是動工前查出來的（便宜），這次是動工後撞到的（貴一點，
  但還好在同一輪內）。
